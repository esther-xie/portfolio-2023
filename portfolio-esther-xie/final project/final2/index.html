App name: Standup

Pitch

Asynchronously organizing and tracking group project progress can be really difficult. There are countless applications existing for managing team projects. However, none of them are really useful for students working on group projects at school. Firstly, apps like notion and trello are heavy-weighted, requiring a lot of effort to set up. Enterprises usually have a fixed top-down fixed workflow, while student projects have much more diverse structures and students want more freedom in organizing their time. Secondly, traditional planning apps are not as effective for students, as we often find it difficult to hold teammates accountable for checkpoints. Many students simply stop replying to group messages when they are distracted by other things.

Introducing Standup, a unique team project management for students. Our product will provide a platform to encourage more communication and collaboration among students. Unlike traditional enterprise project management apps that require a team manager to set up checkpoints in a top-down manner, Standup encourages students to post their progress as desired either to keep record for themselves, or to call teammates’ attention. Students can post “updates” in a blog format with tags, which can be reviewed and reacted to by teammates. Users can remind their teammates when they haven’t updated their progress for a long time, or require their teammates to react to their updates, in order to keep everyone on track. On the other hand, students are also encouraged to express appreciation towards each others’ work and to learn from each other.

Through encouraging students to review each others’ progress and provide feedback, we believe StandUp can facilitate healthier teamwork among students and create a more participatory learning environment.

Conceptual design

Name: Project

Purpose: Overarching folder for updates, and associates with a group of users (teammates)

Operational Principle: When a new project is created, it is associated with one or multiple users. Users can optionally set several dates for required updates, which expect all users to post updates before those dates.

States:

  • project name: Project -> one String
  • active: set Project
  • archived: set Project
  • participants: Project -> set User
  • updates: Project -> set Updates
  • date created: Project -> one Date
  • date archived: Project -> lone Date
  • scheduled updates: Project -> set Date

Actions:

  • user u creates a project
  • user u edits a project
  • user u archives a project
  • user u joins a project
  • user u quits a project

Name: User

Purpose: Authenticate the user, gives users long lasting sessions after the authentication, and remembers user information such as participating projects

Operational Principle: After a user is created, it is associated with the user’s log-in information including user’s full name, password, linked email, participating projects etc. When a person logs in as the user, the app creates the session with all the preferences.

States:

  • firstname: User -> one String
  • lastname: User -> one String
  • password: User -> one String
  • email: User -> one String
  • projects: User -> set Project

Actions:

  • creates a new user
  • sign in as the user
  • sign out as the user
  • delete the user

Name: Update

Purpose: Serve as a standardized unit of progress information

Operational Principle: When a user wants to post work progress they’ve done, they can create an Update containing the information required for each Update. Other users working on the project will then be able to see the Update. The user can also edit their Updates if necessary.

States:

  • dateCreated: Update -> one Date
  • dateModified: Update -> one Date
  • author: Update -> one User
  • summary: Update -> one Text
  • details: Update -> one Text
  • todos: Update -> set Texts
  • blockers: Update -> set Texts
  • status: Update -> one Status (enum)
  • project: Update -> one Project

Actions:

  • user u posts an update
  • user u edits an update
  • user u deletes an update

Name: Comments

Purpose: Allow for further discussion on work that someone did

Operational Principle: User A gave an update. User B wants to offer a suggestion based on their update or ask a question and adds a comment. User A sees this comment when looking at the updates and adds another comment in reply to User B under the same update.

States [Update.Update]:

  • Comment: Update.Update -> set String
  • Author: Comment -> one User.firstname, one User.lastname
  • Date: Comment -> one Date

Actions:

  • User creates a comment to an update
  • User deletes a comment to an update

Name: Eyes Wanted

Purpose: Allow users to flag or bring immediate attention to certain items

Operational Principle: When a user adds an update to a project, they can flag the update with “eyes wanted”. Now, the other team members of that project will see the update on their feed as part of a reading list. The update is also highlighted when viewed with other updates. Only when that team member views the update and marks it as read does it get unflagged for them.

States [Update.Update]:

  • targetUser: EyesWanted -> set User
  • update: EyesWanted -> one Update.Update

Actions:

  • user u flags update v with eyesWanted
  • user u dismisses eyesWanted e
    • allowed only if user u is one of the targetUsers of e

Name: Tag

Purpose: Allow users to categorize updates

Operational Principle: When a user creates a project, they can initialize a list of tags to be used. This way, when a team member adds an update to that project, they can select from the list of tags. During creation of an update, if there is a new tag that the user wishes to use, then they can initialize it on the spot, allowing the team to also tag their future updates with it. The user can also edit the set of tags associated with an update after creation. When the user views all of the updates pertaining to a project, they can filter by tags.

States:

  • tags: Project -> set Tags
  • update: Tag -> one Update
  • label: Tag -> one String

Actions:

  • user u adds tag(s) to project p
    • allowed only if user u is a collaborator of project i
  • user u adds tag(s) to update v.
    • allowed only if user u is a collaborator of the project associated with update v
    • tags are associated with update v.
    • tags are added to the set of all tags.
  • user u removes tag(s) from update v
    • allowed only if user u is a collaborator of the project associated with update v
    • tags are disassociated with update v.
    • tags are removed from the set of all tags.
  • filter on a set of tags
    • sets currently filtered tag.

Name: Thanks

Purpose: Show appreciation for teammates who are on top of their work

Operational Principle: After user A posts an update, user B sees the update and appreciates the work that they put in. They give the update a thanks. User A’s total number of thanks increments by one.

States: [Update.Update]

  • thanks: User -> set Update.Update

Actions:

  • User gives thanks to an update
    • Allowed if user is not the author of the update
  • User removes a thanks from an update
    • Allowed if user issued the thanks
  • User views the number of thanks they have themselves

Name: Poke

Purpose: Remind users to post updates

Operational Principle: User A has not given an update in a week. User B pokes user A for an update. User A gets a popup on their application that reminds them to post an update.

States [User.User]:

  • Poke: User -> one User
  • PokedTime: one Date
  • LastUpdated: User -> one Date

Actions:

  • User pokes another user
    • Allowed if poked user has not submitted an update to the project in the last 7 days
  • User gets poke notification

Wireframe

VSD analysis

Stakeholders: Non-targeted Use

Although Standup is intended explicitly for use in group projects, it could very easily be also used in a corporate setting (see Work of the Future section for details!) As with many other productivity-focused apps, Standup could also be used by individuals on personal projects. Furthermore, Standup is essentially a shared, structured blog, so aside from productivity purposes, it could even be used socially as a way for people to stay in touch with their friends, families, or partners that live far away, by using Updates to share new things happening in their lives. Usage in the workplace will likely be similar to usage in group projects, with a major difference being that the number of people working on a project may be much bigger, and people may belong to a lot more projects, depending on the structure of the company. The Project and Tags concepts would help keep teams and tasks organized, and the different views and Eyes Wanted feature would help busy professionals keep up-to-date on multiple Projects they may be involved in. For personal use, some of the features (e.g., Thanks, viewing by User) might be a little bit less useful, but also don’t hinder the user’s experience. For social use, the structure of an Update lends itself to a bit of a journal format. The Thanks feature could be used to show someone support for what they’ve shared, and the Poke feature could be used in a friendly way to ask how someone is doing.

Stakeholders: Direct stakeholders

Direct stakeholders could include students, TAs/teachers, and (in the case of enterprise use) employees and managers. Students and employees are looking to keep up-to-date with the work of their peers, and are interested in being able to easily find relevant and complete information. The Update feature helps standardize and organize progress information. Students and employees might be concerned that using Standup will cause their work to be too closely scrutinized. To address this, we’ve done our best to keep our focus on updating our peers on the work we’ve done, rather than monitoring each other (e.g., using the Thanks concept to provide positive reinforcement for updating, rather than providing ways to require daily updates.) TAs, teachers, and managers might wish to join the Projects of their students or employees so they can keep up-to-date on the students’ work. This would be possible simply by creating an account and adding their User to the Project. This might pressure students and employees to be perfect in each update they post, though; we don’t plan to incorporate this into our design since it’s primarily intended for use among peers, but this could be resolved by introducing a new Manager type of role where they only see summaries, or certain Updates intended specifically for managers.

Time: Work of the Future

Standup tries to address issues of accountability and responsibility, particularly in remote working situations. As a result, we should be careful to prevent its improper use in the workplace, as technology can enable more precise employee monitoring, and we do not want to help foster an unhealthy work environment. We’ve already seen some of these effects taking place with some companies using tracking software (screen monitors, webcam recording, logging hours, etc.), especially during the pandemic, and we want to make sure we contribute to a healthy, productive environment rather than one where employees are surveilled and punished for, say, not making enough updates. To accomplish this, our Thanks feature encourages users to make updates by allowing them to receive appreciation from their peers. While the Poke feature aims to encourage quieter users to update more frequently, nothing is mandatory, and the window for updating is fairly relaxed: you can only Poke a user if they haven’t updated for an entire week, which prevents requirements such as mandated daily updates.

Pervasiveness: Widespread Use

Since access to Updates is limited to members of a specific Project, the effects of widespread use are less apparent than on a platform where all information is accessible by almost everyone. Given how information shared in updates may be sensitive or considered intellectual property, we chose to not allow updates to be viewable by people outside the organization. We also designed user interactions to be relatively insular within a Project, because our use case generally does not involve too much interacting outside of a project group. We could potentially create profiles to allow users to see what Projects other users are part of. If this is public information and Standup becomes widespread, however, people creating Projects for personal use may want to create separate personal and professional accounts to protect their privacy. As more students and employees begin using Standup, they might grow accustomed to using Standup in the place of traditional standup meetings and meeting notes, which would save a lot of time and efficiency in both publishing and referring back to the information. The number of users in a Project might become very big for certain organizations, so it’s possible we may start needing organization even with the axes (e.g., there are so many updates for a certain task on a certain day that even scrolling through those can become difficult.) This might be addressed with a search function. The number of Projects a user is part of may become very big, if everyone starts using Standup. This may present some organizational problems in finding a specific Project. Being able to access all your Projects from the same account, though, is good for efficiency. As the number of Standup users increases, users may also have many completed Projects as well. This is not much of a problem for the average student with one or two group projects per semester, but as we expand into more general use we may want to consider implementing an archiving feature to keep completed Projects out of the way. Tradeoffs

Thanks?

To make Standup a more interactive platform, we included a thanks concept in response to an update. This inspired a larger idea of potentially gamifying the standup process, or adopting a concept similar to karma. Naturally, with positive feedback, do we want negative feedback as well? Would limiting one user to one thanks per time frame provide a more meaningful source of feedback? With this concept, we considered various options, including: Should thanks be private or public? Should thanks be a limited resource? Should there be negative feedback? Should a more general karma concept be adopted?

We decided to have the thanks concept be private. While having a public count of thanks can be an interesting metric that could be helpful to people working in groups to find people that are quality team members, this could negatively affect users of the application. Similar to social media likes, having a public count of affirmation can lead to comparison and unnecessary competition. Additionally, since this is used in the work context, if potential employers were to use this metric for evaluation of team members, people may refrain from giving thanks in order to inflate their own number. For this reason, we decided to keep thanks private to stay true to its purpose of providing positive encouragement.

We decided that thanks would not be a limited resource and instead would function similarly to a “like” on a social media post. While a more limited resource of thanks might increase its significance and feel more rewarding to receive, it limits the amount of feedback that is given generally. We feel that it is more important to have more interaction, rather than giving a larger reward.

We decided on not including negative feedback. While it makes the feedback system more holistic and encourages diverse thoughts, this feature could induce a negative experience for users. Especially because Standup is used for work projects, negative feedback in response to updates might not be appropriate. We do not want the application to potentially be misused.

We decided that we would stick with a more by-update thanks system, rather than a general karma system. With a karma system, it would encourage people to use the application often. However, it also allows for people to exploit the application and post many updates that do not have any meaningful content just to increase their karma score if every update gave some amount of karma. Overall, for the purpose of our application to encourage more updates from a team member, having a simple by-update thanks system seemed more appropriate, especially if there is no negative feedback.

Poking Frequencies

Inspired by the Facebook poking feature, we wanted a way of increasing interaction and reminding users to post updates. However, Facebook’s poking feature can easily be spammy. The main tradeoffs taken into consideration were questions on how to reduce the spammy nature of pokes and make them more meaningful. Some options we considered were: Limit poking per day/week Enable poking based on the most recently posted update Enable poking only if they haven’t been poked already

In the end, we decided on combining all of the options to stay true to its purpose. Since poking’s intention is to remind users to post an update, it only makes sense to enable poking if the user hasn’t posted something. While limiting poking based on a time frame is a good way to reduce spam, it does not reduce frustration of having already updated and still receiving a notification. However, we also want to be able to poke someone multiple times if one poke was not effective. We also don’t want to poke someone if they have already been reminded by someone. Thus the combination of all of these ideas provide a way for users to poke another user only if they haven’t posted recently, haven’t already been poked by someone else, and haven’t already been poked recently.

Enforcing Timely Updates

Our initial vision was that the application would provide more structure to the update process by enforcing a timeline that updates should be sent, for example every week. This would help encourage users to update more often. However, this imposes a strict timeline that may not fit for some projects. We were considering: Enforcing timely updates Not enforcing updates by some timeline In the end, we decided on not enforcing updates by a time range specified in the application. While this would have served well to encourage more updates, this did not allow for the flexibility of variable deadlines, which occurs often in both student project settings and workplace settings. Additionally, we were able to still somewhat enforce more timely updates with the poke feature so that there is still an avenue for users to remind others to post updates.

Plan for when things go wrong

For regular debugging problems or minor design decisions to make, we’ll plan to ask the group if anyone is available to help or conduct an asynchronous meeting to make decisions, moving along as long as one other person agrees. If necessary, we will not implement some additional features such as comments, as they are not central to the application and of course sacrifice styling the web page in favor of core components. Some features that we may choose to omit if necessary include editing tags and editing updates. Concept-wise, we may choose to omit the concepts of comments, thanks, pokes, and eyes wanted in the respective order if running out of time (meaning we prioritize implementing the latter first).
